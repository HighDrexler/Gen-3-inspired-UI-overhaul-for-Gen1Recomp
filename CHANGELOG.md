# Changelog

## v3.0.0

**Release promotion + hard native battle UI invariant.** `HIDE NATIVE BATTLE UI` is now treated as a battle-wide master guarantee rather than a sibling of the ordinary presentation toggles. Its ownership decision wins before full-frame renderer deferral, so an active CBE/Stadium/portable battle-world provider can no longer be interpreted as permission for Gen1Recomp's original HUD/text/menu chrome to draw. The public `uiOwnership` contract advances to API v3 with `hardHideNativeBattleUi(state)` for provider-side integrations.

Hard hide now also forces the already-supported custom presentation for battle-pushed auxiliary states even when their individual toggles are OFF: Gen I/II dialogue and Yes/No, Party/Summary, Bag/item targeting, move-learning/forgetting, Gen I level-up StatBox, and Gen II FeatureParity service states such as MoveDeleter. Native update/input/callback lifecycles are preserved; where a native draw performs lifecycle work it is executed under a zero-area scissor instead of being skipped. Gen I level-up is explicitly kept usable under hard hide by rendering the modern stat card rather than merely suppressing the native one.

**Runtime-integration validation before packaging:** the full 3.0.0 mod chunk was loaded and initialized in executable Lua for both generations against current Gen1Recomp battle method contracts. With hard hide ON and BATTLE UI / DIALOGUE / POKéMON MENU / BAG / LEVEL-UP / MOVE DELETER / SERVICE toggles deliberately OFF, the harness verified zero original battle-UI pixels through the direct battle HUD/text seams, launcher visibility hooks, Battle Art suppression contract, Dramaless/Dramatic-style HUD wrappers, pushed dialogue/menu states, and an active full-frame renderer. It then ran 750 repeated draw frames per generation and a provider-off vanilla-environment pass; Gen II retained battler picture content while status/bottom UI remained suppressed. A final negative control turned hard hide OFF and confirmed native fallback still renders. Full details and the graphical-runtime boundary are recorded in `VALIDATION_3.0.0.md`.

No user-facing option key, Gen1Recomp module dependency, hook registration, event registration, manifest compatibility field, generation target, or existing named function from v2.1.38 was removed.

Existing `mod.options_changed` handling and direct in-mod option writes invalidate/update the cache immediately.
- Cached loaded mod handles for full-frame battle-environment compatibility. Live `battleWorld` / `battleFullFrame` status and `presentationOwnership()` are still read on every ownership query, so CBE, Stadium-style renderers and future compatible providers can change ownership dynamically; only repeated loader-status allocation and `mod.find()` scanning were moved out of the per-frame path.
- Added keyed geometry caches for battle-menu scale and the shared logical/full-screen canvases. Window dimensions, mobile mode and UI BOX SIZE remain cache keys, so resize and setting changes reproduce the exact existing geometry.

- Removed the second legacy Dramaless/Dramatic Shape HUD wrapper layer. `GoldCompat.patchShapeHudCompat()` was already wrapping the same methods with the stronger generic full-frame-provider defer rule; retaining both only added wrapper depth and could let the weaker layer win. **Regression contract:** Gen I + Gen II targets, option/feature keys, hook/event registration counts, optional dependency IDs and native gameplay callbacks remain intact. The source parses successfully with Lua, and the release archive passes integrity checks.

## v2.1.36

**Cleaned up the Gen 2 TM/HM move-replacement rows so the selection indicator and move text remain aligned under every typography setting.** The previous panel used a row-height estimate plus a fixed move-label size. With larger TEXT SIZE values or fonts whose real line box is taller than PlainPixel, the text could extend below its dark focus plate, separator lines could run through labels, and the font-glyph `>` cursor could sit on a different baseline from the selected move.

The four replaceable rows are now laid out from the exact font metrics used by `partyText()`. Each row receives one quarter of the available move area, the move text shrinks only when the active font/size genuinely cannot fit that row, and both the label and PP value are vertically centered from the measured line height. The selected focus plate uses the same row geometry, while the old font-based `>` has been replaced by a centered geometry cursor and accent rail so it cannot drift with font baselines. Selected and unselected move names now use the same left edge, PP has a measured fixed column, and long move names width-fit through the existing font renderer instead of being truncated by character count. The incoming move label and footer also use width-fitting rather than fixed character assumptions.


## v2.1.35

**Fixed Gen 2 mid-battle Pokémon switching leaving the battle and showing the literal overworld behind the Party menu.** The v2.1.31 workaround forced `PartyMenu.bgMode()` to `"world"` when a full-frame renderer such as CBE was detected. Reading the current Gen1Recomp `Game2:drawScene()` compositor makes the regression unambiguous: in Gen 2, `"world"` does not mean “keep the current battle world”; it explicitly calls `self.world:draw()`, i.e. the overworld map. Because the Party menu is also the top widescreen owner, the underlying `BattleState:drawWidescreen()` was skipped for that frame, so the mod was literally replacing the battle surface with the map during a switch.

The Gen 2 Party menu now acts as a **battle-surface proxy** whenever a live `BattleState` exists below it. It remains the top widescreen state so Gen1Recomp does not enter its duplicate centered-stack composition path, but its widescreen draw first delegates exactly once to the real underlying `BattleState:drawWidescreen()` and then draws the hanging Party deck over that result. This is provider-agnostic: vanilla battle backgrounds, CBE, Stadium-style environments, or any other renderer that owns the normal BattleState widescreen seam remain authoritative. No CBE ID/API special case, frozen screenshot, or overworld substitute is used. The Party proxy also mirrors the live battle's fill-scale, panel dimensions, panel scale, `bgMode`, and surround dim so alternate battle layouts and the user's real BATTLE BG setting remain intact. Outside battle, Party continues to use the existing `"world"`/zero-dim contract so the normal START-menu Party screen still hangs cleanly over the overworld.

## v2.1.32

Three bugs from testing v2.1.31's rebuilt Move Manager: it never appeared at all on the Gen 1 side, Gen 2's version couldn't be exited once opened, and both generations' panel frames showed the same thick black border already fixed elsewhere in this mod. All three were reproduced and confirmed fixed by actually executing this mod's code against the real Gen1Recomp engine source in an isolated Lua harness (mocking only `love`/`bit`), rather than by re-reading the code and guessing -- worth doing more of, given how much time guessing had already burned this round.

**Root-caused and fixed the Gen 1 Move Manager never appearing at all.** v2.1.31 only opened it when `input:wasPressed("select")` fired while `self.page==2` (the CURRENT MOVES page) -- but a Summary screen always opens on page 1 (STATS), and Gen 1's native SummaryMenu never advertises the feature anywhere, so a player who pressed SELECT right after opening a Pokémon (the natural first thing to try, and how Gen 2's version has always accepted it) got no response and had every reason to conclude the feature simply wasn't there. Gen 2's own entry point never had this restriction -- it already accepts SELECT from either page by briefly forcing GREEN_PAGE open first. Removed the `page==2` requirement from Gen 1's hook so it now matches Gen 2 exactly: SELECT opens the manager from either page. Also added the "SELECT: MOVE MANAGER" footer hint to Gen 1's STATS page (page 1), matching the hint already shown on MOVES (page 2), so the feature is discoverable without needing to flip pages first.

**Fixed the Move Manager being impossible to exit once opened (Gen 2).** Confirmed via the isolated engine test: pressing B correctly cleared this mod's own `__gen3uiMoveManager` state, but left Gen 2's native `moveDetail` field (and `swapFrom`) untouched -- and both the `SummaryMenu.update` wrap and `drawGoldSummary`'s fallback treat "`moveDetail` true, no manager open" as "the native MOVES row was just pressed, open the manager," which is exactly what happens on the very next frame. From the player's side, B appeared to do nothing at all. Now clears `moveDetail`/`moveScreen`/`swapFrom` alongside closing the manager, so backing out actually returns to the plain moves view instead of reopening itself immediately. Harmless on Gen 1, which has no such fields.

**Fixed the Move Manager's own panel frames showing the same thick black border already fixed for the party list back in v2.1.30, on both generations.** This screen's card chrome (the move-list panel and the MOVE DATA/REPLACE WITH panel) was carried over unchanged from v2.1.30's old reorder-only Move Manager, which itself was never given the softened treatment `partySlotPanel` got -- a thick, fully opaque near-black double-rounded-rect reads as a stark black box at this canvas's render scale, exactly the same complaint as before. Replaced with the same soft-shadow-plus-thin-outline treatment already proven on the party cards: a low-alpha drop shadow, the cream face, and a single-pixel warm outline instead of a filled dark inset.

## v2.1.31

Five items from one round of testing: the Gen 1 field-move submenu's cursor centering, a fully non-functional Gen 2 Move Manager rebuilt from scratch against a working reference the user supplied, a Gen 2 TM/HM badge that marked every Pokémon as ABLE regardless of whether it could actually learn the move, an enemy trainer sprite popping up over a full-frame 3D battle renderer, and a solid black screen when switching Pokémon mid-battle.

**Rebuilt the Move Manager from scratch on both generations, replacing v2.1.30's Gen 2-only design outright -- confirmed non-functional by direct user report ("the move manager does not work at all still").** No root cause in the old START-triggered picker was conclusively found before this rebuild started, and rather than keep guessing at a second from-scratch design, the user supplied their own Colosseum Inspired UI Overhaul mod -- a sibling reskin of this same engine, sharing this mod's own architecture (the same GoldCompat namespace and drawing helpers), confirmed by the user to have "a fully functional move manager on both gens." Reading its actual implementation rather than re-deriving one turned up the real flaw in v2.1.30's design: it tried to bolt a picker onto native's own reorder-only state machine via a separately-discovered button, instead of replacing that state machine outright. This rebuild follows the reference's proven flow instead: highlight one of the mon's 4 current moves and press A to manage it, then choose either DELETE MOVE (always listed first) or any move it can currently relearn, and press A again to apply. The relearnable pool combines the species' real level-up learnset -- walked back through every pre-evolution, so an evolved Pokémon can still relearn an early-stage move, filtered to the mon's current level -- with a per-mon history of every move ever seen on it through this same manager, recorded the moment it's opened and whenever a move is changed, since neither game's engine keeps that history natively (confirmed by reading both engines' source) and level-up data alone can't reconstruct a forgotten TM/tutor move. Field names are read defensively for both real schemas at once, confirmed against `src/mods/Schemas.lua`: Gen 1's species data carries `level1Moves`/`learnset` and evolutions keyed by `species`, Gen 2's carries `levelMoves` (level-1 moves included) and evolutions keyed by `into` -- this mod's own pre-existing `GoldCompat.summaryLevelUpLearnset` only ever read the Gen 2 shape, which would have silently found nothing at all for Gen 1.
- **Gen 2**: SELECT on the moves page opens the manager exactly as v2.1.30's picker did (still confirmed unused anywhere in the real `SummaryMenu.lua`'s input handling), and the party field-submenu's native "MOVES" row now opens the same manager too, instead of falling through to native's bare reorder screen.

- Kept the writing choice from v2.1.30's design: applying a change writes the new move using the same entry shape and raises the same `pokemon.move_learned` event Gen 2's own `Mon.learnMove` uses for every other new-move grant, so any other mod hooking that event sees this as a genuine learn.
- Reskinned into this mod's own existing cream-panel MOVE MANAGER layout (the 4-move list plus detail panel already built for v2.1.30's Gen 2 screen), not the reference mod's own dark visual theme -- per this project's standing requirement that a ported mechanism gets its own presentation, never Colosseum's.

**Fixed Gen 2's TM/HM party picker marking every Pokémon as ABLE regardless of whether it could actually learn the move, confirmed by screenshot showing an entire party all marked ABLE for the same move.** Root cause, confirmed against the real `src/ui/gen2/PartyMenu.lua:972-981`: the native `PartyMenu:tmhmAble(mon)` method returns a STRING (`Strings(ABLE_LABEL)` or `Strings(NOT_ABLE_LABEL)`), not a boolean -- both possible real results are non-nil, so this mod's `self.tmhmAble and self:tmhmAble(m) or false` check was testing the string's mere existence, which is always true, rather than which string it actually was. Fixed by deriving the boolean directly the same way Gen 1's own already-correct hand-derived version does: checking the target species' own `tmhm` list for the taught move's id, rather than trusting the native method's return value as a boolean.

**Suppressed the enemy trainer's switch-in sprite overlay when a full-frame 3D battle renderer (such as CBE) owns the battle, confirmed by screenshot showing it floating over a rendered arena.** This overlay (`GoldCompat.drawGoldTrainerSwitchOverlay`) was verified correct, genuine vanilla presentation back in v2.1.27 -- and still is, for this mod's own default 2D presentation. This mod's own `PartyMenu.bgMode` delegate now additionally forces "world" specifically when a full-frame 3D renderer is confirmed active for that battle, on the reasoning that such a renderer's own 3D scene is what should show through rather than the real battle's configured 2D background. This part is flagged honestly as a best guess rather than a confirmed fix: a full-frame renderer such as CBE is a separate, companion mod, and this project has no access to its source to confirm it actually treats this signal as "keep compositing your scene here" the way this fix assumes. ## v2.1.30

Four items from one round of testing: a Gen 1 submenu with an off-centered selection cursor, the TM/HM integrated dialogue box burying the move-replace panel it sits over, the party card border still reading as opaque after v2.1.29's softening pass, and the Move Manager's scope correction (it needs to replace moves from the learnset, not just reorder the existing four) -- this last one actually built for Gen 2, honestly scoped for Gen 1.

**Fixed the Gen 1 field-move submenu's (SURF/STATS/MOVES/SWITCH/CANCEL) selection highlight sitting off-center against its own label, confirmed by screenshot.** This row list hardcoded its pitch (12) and highlight height (11) as constants sized for the default TEXT SIZE, while the label itself is drawn at a fixed `yy+1` offset using a font that grows with the user's TEXT SIZE/TEXT THICKNESS settings. At anything but the smallest setting the label's real glyph height no longer matched that guessed 11px band, so the fixed offset always landed the text near the TOP of the highlight with a growing dead gap underneath -- the exact same class of bug already fixed for the Bag/Pack list back in v2.1.28 (`GoldCompat.bagPackRowHeight`/`dynamicRowHeight`) by deriving row pitch from the label's actual measured font height instead of a constant, one of roughly a dozen menus that sweep covered. This particular submenu (`state.submenu`/`state.subItems` in `drawPartyFinal`) was missed by that sweep. Switched it to call the same `GoldCompat.dynamicRowHeight(6,12,3)` helper (matching the `6` size this submenu's labels actually render at) for both the row pitch and the highlight height, and removed the panel's own hardcoded height cap (`6+count*12`, clamped to 66) in favor of letting it size itself from the real row pitch, so it can't run short of its own rows at larger TEXT SIZE settings the way a still-fixed cap would.

**Fixed the TM/HM integrated flow's dialogue box burying the party card's own move-replace list underneath it, confirmed by screenshot showing FURY CUTTER's row cut off and CUT/SMOKESCREEN/EMBER hidden entirely.** Root cause, confirmed against `src/core/Game2.lua:learnMoveOn`: the "Which move should be forgotten?" TextBox is pushed with `stay=true` and deliberately never popped for the whole time the player is choosing (`pickMove()`'s `onShown` pushes the real move list directly on top of it, and both `onCancel`/`onChoose` pop the list before the question itself) -- so this mod's own standard dialogue box renderer (`GoldCompat.drawDialogueThemeFinal`) is on screen for the entire pick, at its normal 24-42 logical-unit height anchored to the bottom of the screen. The party card's own move-replace rows (`GoldCompat.drawPartyMoveReplace`, shared by both generations' integrations) sit in that exact same bottom slice of the 160x144 canvas (card body `ly=23..124`), so the dialogue box's normal size directly overlapped the very rows the player needs to read to make their choice -- worse at larger TEXT SIZE settings, where the box grows toward its 42-unit cap. Since the box's own paging already only ever shows 2 lines at a time regardless of its height (`visible=math.min(2,#shown)`), a shorter box loses no content -- it just forces a smaller auto-fitted font via the same `fittedCompletedDialogue` sizing already used underneath. Now detects this exact context (`State.activeTMPromptFlow` for Gen 1's `MoveLearnMenu` integration, `State.activeGen2MoveLearn` for Gen 2's) and caps the box at a fixed 16 logical units instead, sized so its top edge lands right at the card's own bottom edge (124) rather than climbing into it. Applies to both generations, since both share the identical card geometry and neither had been specifically tested against a concurrent dialogue box before.

**Redesigned the party card/row frame to actually be transparent, not just a lighter shade of opaque, per direct user correction of v2.1.29.** That build only lightened `partySlotPanel`'s outer edge from near-black to charcoal (`0.24,0.23,0.20`) -- still a fully opaque filled rounded-rect the same size as the card, so every card and row still read as a solid colored box floating over the overworld, just a less harsh one. The ask was literal: "there should not be two large black opaque borders on the pokemon screen, it should be entirely transparent to the overworld." Fixed by dropping the opaque edge fill entirely -- the panel is now just its white face, a barely-visible low-alpha drop shadow (unchanged from v2.1.29, it was never the problem), and a thin 1px outline for legibility against bright overworld tiles, so the overworld now genuinely shows through everywhere except the card's own face. Shared by both generations' party screens as before.

**Rebuilt the "MOVE MANAGER" to actually replace moves from the Pokémon's learnset, not just reorder the existing four -- corrects the wrong scope proposed in v2.1.29 below.** That entry proposed a session-scoped "delete and restore a recently-forgotten move" design; the user corrected this directly: *"the move manager is just a move...manager. The user can move the position of the moves they have but they have no ability to replace their current moves with past learnset moves. Any move that a pokemon can learn up to their level should be available to switch out."* That's a better, simpler design, and it uses data that already exists rather than inventing new session state: `GoldCompat.summaryLevelUpLearnset` already computes a mon's complete by-level learnset from the same `levelMoves` (EvosAttacks) table `Mon.lua`'s own level-up/TM logic reads, so filtering it to `level <= mon.level` and excluding already-known moves gives exactly the replacement pool asked for.
- Built for Gen 2's Summary "MOVE MANAGER" (`GoldCompat.drawGoldMoveManager`, GREEN_PAGE's `moveDetail` mode). Confirmed against the real `src/ui/gen2/SummaryMenu.lua` that its native reorder-only behavior (`updateMoveDetail`/`swapMoves`) really is the entire vanilla feature here -- there's no native "replace" path this mod could reskin the way everything else in it does, so this is genuinely new functionality, not a reskin. Pressing START (confirmed unused anywhere in that file's real input handling, so it can't collide with a native action, the same way this mod already borrows SELECT to enter the manager in the first place) while a move row is highlighted and no move is currently picked up opens a scrollable "REPLACE WITH..." list of every learnable move at or below the mon's current level that it doesn't already know; confirming a choice writes it into that exact slot using the same entry shape and event Gen 2's own `Mon.learnMove` uses for every other new-move grant (`{id, pp=def.pp, maxPp=def.pp}`, then `Runtime.emit("pokemon.move_learned", {mon=mon, moveId=moveId})`), so any other mod hooking that event sees this exactly as it would a real level-up or TM teach.

That's real, separately-scoped work for a follow-up round rather than something to rush in alongside four other fixes.

**The headline fix.** Found a real bug that plausibly explains "the mod does literally nothing on Gen 1": every one of this mod's ~35 `mod.log("error"/"info"/"warn", ...)` calls used the wrong calling convention. The engine's real mod API (confirmed in `src/mods/Loader.lua`) defines `mod.log` as a *table* of methods (`mod.log.info`/`.warn`/`.error`), meant to be called `mod.log:info(...)` -- calling it as `mod.log("error", "...")` instead throws `attempt to call a table value`. The actual damage: this mod's whole overlay render pass (Bag, PC, Party, Summary, Battle HUD, dialogue, the Gold service screens, all of it) is one hook function that calls each screen's `pcall`-guarded draw routine and, *only on failure*, tries to log the error and move on to the next one -- exactly so one broken screen degrades gracefully instead of taking the rest down with it. What this mod DOES do for all of these "hanging over the overworld" screens is skip their native `draw()` call outright whenever its own restyled version is active. That exact pattern -- skipping a native draw call entirely instead of still running it (just invisibly) -- was already found and fixed once this session for the Gen 2 battle HUD, because some native draw methods also advance per-frame state their own update() logic depends on, and skipping them silently starves that bookkeeping. ## v2.1.12

- Fixed the debug badge STILL being unreadable after the v2.1.11 sizing fix (confirmed by user screenshot -- smaller box, correctly sized now, but still zero legible text). Root cause: `GoldCompat.menuPortraitShader()` -- a shader used elsewhere to strip white mattes from Battle Art images by making any near-white pixel fully transparent -- was still bound on the graphics state when the badge drew itself. `love.graphics.push("all")` only *saves* the current shader so it can be restored afterward; it does not clear or disable it for draws made inside the push/pop block. The badge's own text was pure white (1,1,1,1), so the exact same shader that's meant to strip white mattes off Battle Art art was silently zeroing the alpha of the badge's own text, leaving only the solid-color background visible. Fixed by explicitly calling `love.graphics.setShader()` right after entering the badge's isolated draw state, clearing whatever was bound. As additional belt-and-suspenders protection against this exact failure mode recurring, the badge's colors were also changed from white-text-on-red to black-text-on-yellow -- black text can never be erased by a white-stripping shader even if some other shader is ever left bound here in the future.
- This build's badge should now finally be legible. If Battle Art's art is still not appearing in Party/PC/Summary/Pokédex, the badge will show a specific `BA:XXXX` failure code (e.g. `BA:NF`, `BA:LIB`, `BA:MOD`, `BA:IFACE`, `BA:NOIMG`, `BA:NOFRAME`, `BA:NOANIM`, `BA:ROM`, `BA:GEN`) rather than nothing at all -- that code is the next concrete lead.
